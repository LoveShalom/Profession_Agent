### 一、正在尝试解决的实际问题

国内求职者在求职期真实遇到的问题是：

1. **岗位信息分散**：BOSS直聘、猎聘、智联、国聘、NCSS、企业官网、公众号、内推群，各看各的，无法统一管理。
2. **截止时间靠记**：网申截止、笔试确认、面试时间、Offer 答复期限散落在邮件、短信、平台站内信里，容易漏。
3. **投递状态混乱**：投了哪些、到哪一步、要不要跟进、该准备什么，全靠记忆和 Excel。
4. **JD 与简历匹配靠感觉**：不知道这个岗位到底看重什么，也不知道自己差在哪。
5. **经历素材散落，简历反复重写**：实习、项目、科研、社团经历散落在不同简历版本、备忘录和文档里；每投一个岗位都要重新改简历，重复劳动；同一段经历对不同 JD 需要不同写法，但用户不知道突出哪一点；投递多个方向时版本管理混乱，改到最后不知道哪版投了哪家。
6. **材料重复造轮子**：每投一个岗位都要改简历、写打招呼语、准备面试题，耗时且质量不稳定。
7. **现有工具错位**：国外求职工具不适配国内平台；自动爬取、批量投递又有封号和合规风险。

这些问题不是“岗位不够多”，而是“岗位信息没有沉淀成可管理的数据，个人经历没有资产化，投递流程没有变成可执行的系统”。

### 二、核心症结

**核心症结：国内求职过程缺少一个以“个人岗位库 + 个人经历库”为中心的闭环管理系统。**

展开来说：

- **信息层**：岗位是非结构化的，粘贴完就散落各处，无法检索、排序、提醒；个人经历同样没有结构化，缺少技能标签、量化结果、STAR 素材和证据链接。
- **决策层**：没有针对每个 JD 的匹配反馈，投不投、优先投哪个，靠直觉；也不知道目标 JD 最看重哪段经历，该用哪套话术。
- **执行层**：没有状态机和优先级，投递、笔试、面试、跟进无法动态规划；简历是静态文档，无法按 JD 动态组装，每次都要从头修改。
- **工具层**：国外工具水土不服；自动化工具又越过合规边界。
- **心理层**：混乱导致焦虑，焦虑导致乱投，乱投导致反馈更差。

所以本项目要解决的不是“帮你自动投递”，而是**把求职从混乱的手工操作，变成合规、结构化、可规划的个人管理系统**。岗位库管机会，经历库管素材，JD 是连接器——简历不再是反复修改的静态文档，而是从经历库按目标 JD 动态生成的“视图”。

### 三、目标受众

**主要受众：**
- 国内校招应届生：同时投递几十家，网申、笔试、面试流程密集；实习、科研、社团、课程项目多，但不知道怎么写。
- 国内社招 1–5 年求职者：尤其是互联网、技术、产品、运营、设计岗位；项目多、经历杂，需要快速组合出匹配 JD 的简历版本。
- 多平台并行求职者：BOSS、猎聘、国聘、企业官网同时使用的人。
- 多方向求职者：同时投技术、产品、运营等不同岗位，需要针对不同 JD 生成不同话术。
- 注重合规与隐私，愿意手动粘贴 JD 的用户。
- **重视数据隐私、愿意本地部署的用户**（C-10 本地优先的主要受众）：数据全部留在自己机器上，可自带模型 API；一键启动脚本降低门槛。

**次要受众：**
- 国企/央企/体制内求职者：关注国聘、NCSS、政府开放数据。
- 海归回国求职者：不熟悉国内平台和流程。
- 转行求职者：需要把旧经历翻译成目标岗位语言，需要匹配度反馈和材料定制。

**已知使用门槛（E-09 已裁决）**：本地部署需要安装 Docker；一键启动脚本可显著缓解但无法完全消除门槛，完全非技术用户仍偏难。桌面打包（Tauri / Electron）记为 Post-MVP 观望项。

**非目标受众：**
- 想全自动批量投递的人。
- 想爬取非公开数据、采集他人简历的人。
- 需要招聘方 SaaS 的 HR 用户。

### 四、具体算法 / 核心机制

Mission 里不需要锁死实现，但需要说明“靠什么机制成立”。核心是一套 **LLM + RAG + 状态机 + 规则校验** 的管线，覆盖岗位与经历双库：

| 模块 | 输入 | 算法/机制 | 输出 |
|---|---|---|---|
| JD 结构化抽取 | 粘贴的 JD 文本 | LLM + Function Calling / JSON Schema + 规则校验 | 字段字典 v1（公司、岗位、招聘类型、届别、城市、薪资、学历、经验、技能、截止时间等 18 字段，含 evidence 与 confidence） |
| 置信度校准 | 同一 JD 的 K 次抽取结果 | **自一致性**（K=3 一致率）+ 规则复核（无 evidence 强制低置信） | 字段级 confidence（替代"LLM 自报"这一不可辩护的做法） |
| 经历结构化 | 实习/项目/科研/社团原始描述 | LLM + STAR 模板 + 技能标签 + 量化抽取 | 结构化经历条目（含技能标签、量化结果、证据链接） |
| 简历解析（P1） | PDF/Word 简历 | 文本抽取（Node 端 pdfjs/unpdf + mammoth）+ 分段 + LLM 结构化 | 多条经历草稿，逐条确认后进入经历库 |
| 双库向量化 | 经历条目 + JD 字段 | BGE-M3 Embedding（或用户配置的 Embedding）+ pgvector；未配置则退化为关键词检索 | 可检索的岗位库与经历库 |
| JD 定向检索 | JD 结构化字段 | 向量 + 关键词混合召回 Top 10 → 重排 Top 5 | 最相关的 Top N 经历 |
| 匹配评分 | 召回结果 + 结构化字段 | 规则加权打分（技能 0.35/经验 0.25/学历 0.15/城市 0.15/薪资 0.10，缺失维度重归一化），LLM 只生成差距提示 | 五维评分（0–100）+ 三级标签 + 差距提示 |
| 话术生成 | JD + 相关经历 + 匹配结果 | Prompt 模板 + LLM | 简历 bullet、自我介绍、打招呼语、面试回答 |
| 验证器优先生成 | 生成候选话术 + 经历库 | 规则验证（数字/公司/时间字面命中）→ LLM 复核 → 失败则修复重生成 → 仍失败则**弃答** | 带证据、可追溯的材料；不可验证时明确弃答，杜绝编造 |
| 版本管理（Post-MVP） | 岗位 + 话术 + 简历版本 | 状态机 + 版本快照 | 针对该岗位的简历视图，可导出 PDF |
| 动态规划（P2） | 岗位状态 + 时间字段 | 状态机（13 状态 + 转移矩阵）+ 优先级排序 + 定时调度（日扫 + 小时扫） | 待投递、待跟进、待笔试、待面试提醒 |
| **模型接入（BYOK）** | 用户自选的 LLM / Embedding API Key | Provider 适配层（OpenAI 兼容）+ 能力探测 + 降级链（Function Calling → Prompt-JSON → 规则抽取） | 可用的模型能力 + 用量与成本记录 |
| 用户风格检索 | 该用户已确认 / 编辑过的材料 | 从自有产物中检索 few-shot（替代固定的 3 个样本），越用越像你 | 个性化话术（不做微调、不外发数据） |
| 求职记忆固化 | 投递事件 + 已确认材料 | 周期性固化 → 长期记忆卡（偏好、被拒模式、有效话术） | 生成与建议时可直接检索的长期记忆 |
| Agent 生态接入（MCP） | 岗位库 / 经历 / 匹配 / 生成能力 | 以 MCP tools + resources 暴露（本地 stdio，不出网） | 可被 Claude / Cursor 等 Agent 客户端直接调用 |
| 评测与可观测 | 人工标注集 + 调用日志 | Promptfoo / Ragas / LangFuse | 抽取准确率、匹配一致率、成本、延迟 |

**前沿能力的取舍（不是装饰，每条都对应一个真实痛点）**

| 能力 | 对应痛点 | 为什么必要 |
|---|---|---|
| 验证器优先生成 | 6 材料重复造轮子 / 信任 | 材料的价值取决于"能不能用"；不可验证的内容宁可弃答，这是信任底线 |
| 自一致性置信度 | 4 JD 匹配靠感觉 | "LLM 自报置信度"在评审里站不住；用 K 次采样一致率替代，方法学可辩护且能直接进评测 |
| 用户风格检索 | 5 经历素材散落 | 材料个性化不靠微调（数据量不够），靠检索用户自己认可过的写法 |
| 求职记忆固化 | 3 投递状态混乱 | 求职是 2–6 个月的长周期战役，需要长期记忆而非每次从零推理 |
| Agent 生态接入（MCP） | 7 现有工具错位 | 不另造一个聊天框，而是让本项目成为 Agent 生态里的能力提供方（本地、私密、无云端） |
| 查询分解与多跳检索 | 4 JD 匹配靠感觉 | 一条 JD 常含多个独立要求，单次召回会漏；分解后逐项检索更准 |

关键原则：
- **验证优先于生成**：先设计可验证性，再谈生成质量；验证不通过时宁可弃答，也不输出无证据内容。
- **AI 只建议，不自动执行关键动作**；投递和沟通仍由用户手动完成。
- **经历库是唯一数据源，简历是投影**；改一次经历库，多岗位复用。
- **证据优先，禁止 LLM 编造经历**；生成话术必须可回溯到经历条目。
- **模型可替换，密钥属于用户**：所有 AI 调用经可插拔的 Provider 适配层，使用者可自带 DeepSeek/Qwen/Kimi/GLM/OpenAI/Ollama 等任意 OpenAI 兼容端点；密钥加密存储、只写不回读；未配置密钥时降级为规则模式，功能不中断。
- **数据流向透明**：自带密钥时数据只发往用户自己选择的服务商；不用于模型训练。

### 五、项目生命周期

项目按阶段推进，每个阶段都有明确退出标准。**5 周计划（`roadmap.md`）覆盖 P0–P2；P3–P5 为后续阶段，排期待定。**

**P0 概念验证**
- 目标：验证“粘贴 JD → LLM 结构化 → 存库”可行，并抽出 Provider 适配层。
- 产出：本地脚本或简单页面 + Provider 适配层（`.env` 配置模型）。
- 退出标准：字段字典 v1 可用，人工抽检准确率 90%+（第 1 周末过程门 80%）。

**P1 MVP**
- 目标：岗位管理 + 经历库 CRUD + 状态流转；**本地一键启动可用**（C-10 本地优先）。
- 范围：手动粘贴 JD、结构化入库（含自一致性置信度）、状态流转与截止倒计时；手动录入实习/项目/科研/社团经历，支持标签与 STAR 结构化；**从 PDF/Word 旧简历导入经历（A-05 裁决：进入 P1）**；**BYOK 最小版设置页（填 Key + 冒烟校验）**；Provider 适配层与凭证校验；认证**可选**（本地单用户可关闭）。
- **不在 P1 范围内**：提醒与通知（飞书/邮件）、定时调度——按 A-08 裁决后置到 P2。
- 产出：本地可跑的 Web App（Docker Compose + `npm run setup`）+ 无状态只读展示页。
- 退出标准：自己能连续管理 20+ 岗位、录入 10+ 段经历，并成功从一份旧简历导入经历。

**P2 AI 增强（Demo 版第二阶段）**
- 目标：提醒闭环 + 匹配评分 + 定向话术生成。
- 范围：**提醒与通知（飞书 Webhook + 邮件 Resend，日扫 + 小时扫）**、混合检索、五维评分、基于经历库生成针对 JD 的简历 bullet、打招呼语、面试题、跟进建议。
- 产出：AI 模块 + 提醒服务 + Prompt 评测集。
- 退出标准：匹配与人工标注一致率 85%+（周目标 80% 为过程门，口径见 `tech_stack.md` §12.4）；生成话术可回溯到经历条目，无编造；提醒可送达。
- 收尾：5 人以上内测，收集反馈。

**P3 版本管理（Post-MVP，排期待定）**
- 目标：按岗位生成简历视图，支持导出 PDF。
- 范围：版本快照、简历视图、导出（中文字体嵌入 + ATS 友好文本层）、投递记录关联。
- 产出：版本管理模块。
- 退出标准：能回溯“哪版简历投了哪个岗位”。

**P4 合规数据源 + 插件（Post-MVP，排期待定）**
- 目标：定期推荐 + 快速录入。
- 范围：接入国聘、NCSS、政府开放数据等合规源（**仅官方公开接口，开工前先做接口与条款核查**）；浏览器插件侧边栏，手动触发解析当前 JD 和经历。
- 产出：导入入口 + 每日/每周推荐 + Chrome/Edge 插件。
- 说明：国聘/NCSS/政府开放数据与邮件解析（**D-01 ~ D-03 已裁决**）先列入待办，核心功能完成后再考虑。
- 退出标准：不碰非公开数据，不自动投递。

**P5 开源 / 迭代（Post-MVP，**E-05 已裁决为优先阶段**）**
- 目标：形成可写简历的作品，并让使用者真正能用自己的模型跑起来。
- 范围：**完整多 provider 设置页（含任务级模型偏好）+ 密钥轮换 + 用量面板 + 一键启动脚本三平台验证 + README/ADR/评测报告**；开源发布。本地 Docker 自托管已是主路径（T1），不在此阶段。
- 产出：GitHub 仓库（含一键启动与自托管说明）+ 无状态只读 Demo。
- 退出标准：可展示、可讲述、可迭代；他人在自己机器上按 README 跑起来并接入自己的模型 API。

### 六、最终 Mission 陈述

> 为国内求职者打造一个**合规、AI 原生、本地优先的求职副驾驶**：统一管理岗位机会与个人经历资产，通过手动粘贴或合规数据源导入岗位，用 LLM 将 JD 和经历结构化，用 RAG 做匹配与检索，针对目标 JD 动态生成简历要点、打招呼语和面试话术。它不自动投递、不爬取非公开数据，而是让用户一次维护经历库，多岗位生成定制版本，把分散的岗位信息和混乱的求职流程，变成可管理、可执行、可复盘的个性化求职系统。
>
> **本地优先（C-10 裁决）**：项目以开源形式发布，使用者从 GitHub clone 后在自己机器上一键启动，**岗位、经历、简历等个人数据全部留在本机**（仅在你主动触发 AI 功能时，把必要文本发给你自己配置的模型服务商）；作者不托管、不存储任何用户数据，也不承担模型费用。使用者可自带任意 OpenAI 兼容的大模型 API（也可本地 Ollama 全离线），密钥加密存储、只写不回读。在线仅保留一个**无状态只读 Demo** 用于展示。
