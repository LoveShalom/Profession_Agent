# Roadmap（功能增量驱动版）

> 术语与功能编号见 [logs/README.md](../logs/README.md)。本文**不按日期划分工期**，按**可独立验收的功能增量**划分；日期只作为容量校准的软参考。

## 0. 为什么改成按功能划分

| 原设计（按周/日排期）的问题 | 新设计（按功能增量） |
|---|---|
| 日期一漂移，整张表失效（首周已漂 2 天） | 增量以"出口标准达成"为完成标志，不受日期漂移影响 |
| 跨周任务被硬切断（如简历导入跨 10/22–10/26） | 功能项从"未开始"到"已验收"完整归属一个增量 |
| 回答不了"这个功能做完没有" | 进度 = 已验收功能项 / 该增量功能项总数 |
| 排期与范围相互绑架 | 范围由增量定义，节奏由容量预算约束 |

**三层结构**：`增量（Increment）` → `功能项（A/F/B 编号）` → `验收标准（DoD）`。
**日期的两个作用**：① 总容量预算（35 天 ≈ 190–220 小时）；② 里程碑的软锚点。仅此而已。

## 1. 进度管理规则

### 1.1 功能项状态机

```text
未开始 ⬜ ──→ 进行中 🟡 ──→ 待验收 🔵 ──→ 已验收 ✅
                  └────────────→ 已延期 ⏸（需在周复盘记录原因与新的目标增量）
```

- 一个功能项**只有"已验收"才算完成**，代码写完不等于完成。
- **不接受"部分完成"**：若一个功能项无法整体验收，就拆成更小的功能项。
- 完成率 = `已验收功能项数 / 该增量功能项数`（按 `A/F/B/R` 编号统计，可直接映射到 GitHub Issue / Projects）。

### 1.2 验收标准（DoD）代码

| 代码 | 适用类型 | 通过条件 |
|---|---|---|
| **D1** | 数据层 / migration | migration 可正向执行且可回滚；RLS 双用户越权用例通过；索引已建 |
| **D2** | 抽取 / 生成类 AI 功能 | Promptfoo 达标（口径见 `tech_stack.md` §12.4）+ 单元测试覆盖；有 baseline 对比 |
| **D3** | UI / 交互 | 手动主路径跑通 + 空状态/错误态可用 + Playwright E2E 覆盖 |
| **D4** | 服务 / 基础设施 | 单元测试 + 失败重试与降级路径均验证过（含无密钥、无 Embedding 的降级） |
| **D5** | 文档 / 发布物 | 5 分钟能读懂；他人可按说明复现（视为"用户"验收） |

### 1.3 节奏

- **每日 30 分钟**：更新功能项状态，写下一条阻塞。
- **每周日 30 分钟复盘**：只做两件事——重排"未开始"的顺序、把"已延期"项指定到新的目标增量；**不新增范围**。
- **增量关闭条件**：该增量全部功能项"已验收" + 出口标准人工确认，才允许把增量标记为完成。

## 12. 前沿能力增量（Frontier Layer）

> 来源：`tech_stack.md` §3.9。原则是**只做能进评测的**，并且**不增加总工时**——前沿能力的时间全部从 I7（提醒，已是最小版）让出。

### 12.1 已并入 5 周计划（3 项，共 +8h）

| 编号 | 能力 | 并入增量 | 成本 | 判定它"做成了"的证据 |
|---|---|---|---|---|
| A15 | 自一致性置信度（K=3 一致率替代 LLM 自报） | I1 | +4h | 置信度**分层准确率**：高置信字段比低置信高 ≥15pt；`一致率≥0.9` 字段占比可报告 |
| A14 | 验证器优先生成（含弃答） | I6 | +2h | 规则验证 / 修复 / 弃答四条路径都有测试；弃答率 ≤15%；幻觉率 ≤2% |
| A16 | 用户风格检索（自有产物做 few-shot） | I6 | +2h | 30 条话术样本 A/B：人工评分提升 ≥10% |

**为什么是这三项**：它们分别解决了"置信度不可辩护""材料不可信""材料不像你"三个评审最容易追问的点，且都能用现有评测集直接量化，边际成本 1 天以内。

### 12.2 触发式增量（不占 5 周工时，条件满足才做）

| 编号 | 能力 | 触发条件 | 成本 | 备注 |
|---|---|---|---|---|
| A19 | MCP Server | P5 开源化启动时（**默认包含在 P5**） | 8h | 让项目成为 Agent 生态的能力提供方；本地 stdio，默认只读 |

### 12.3 明确不做（写进 ADR 或本表以免反复讨论）

| 不做 | 原因 |
|---|---|
| 微调 / DPO / RLHF | 单用户数据量不足，且与"本地优先、不训练"原则冲突 |
| 多 Agent 框架（LangGraph / CrewAI 等） | 当前流程是确定性的管线，引入编排框架只增加调试成本 |
| 自主浏览器 Agent | 与合规红线直接冲突 |
| 为所有功能加 RAG | 结构化字段查询比向量检索更准，滥用 RAG 会降低精度 |
| 约束解码（grammar-based） | BYOK 下模型异构，可移植性差；Function Calling + Zod 已足够 |
