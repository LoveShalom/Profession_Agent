# F-04 截图 OCR 输入

## 0. 元信息

| 项 | 内容 |
|---|---|
| 编号 / 名称 | F-04 截图 OCR 输入（图片 → 文本 → 复用 JD 抽取管线） |
| 所属增量 | **I1.5**（与 F-03 同增量，共 18h） |

**一句话定义**：有些招聘网站不让复制文字，那就**直接把截图粘进来**，系统认字后走和粘贴文字完全相同的解析流程。

> 需求出处：用户提出"解析 JD 时的输入可以用解析截图文字的方式来做，因为有的网站不允许复制，
> 就可以使用输入截图的方式来提取 JD"（[decisions_log §15](../../logs/decisions_log.md)）。
> 用户裁决：**并入 I1.5**（不在 I1 补做）。

## 1. 功能规格与分支

### 1.1 用户故事

- **US-1**：作为求职者，当招聘网站禁止复制（选中即弹登录/水印），我希望截图粘贴后系统自动认字，
  以便不用手打两屏 JD。
- **US-2**：作为求职者，我希望一次能贴多张图（或一张很长的手机长截图），系统按顺序拼成完整 JD。
- **US-3**：作为关注隐私的用户，我希望知道"这张图会被发到哪个服务"，并能在纯本地模式下完成识别。
- **US-4**：作为没有视觉模型的用户（例如只用 DeepSeek 文本模型），我希望系统告诉我该怎么配，
  而不是直接报"不支持"。

### 1.2 输入 / 输出契约

| 项 | 内容 |
|---|---|
| 输入 | `ImageInput { images: Array<{ data: Uint8Array, mime: 'image/png'\|'image/jpeg'\|'image/webp', name?: string }>, order?: number[] }`；1–5 张，单张 ≤10MB，合计 ≤30MB |
| 中间产物 1 | `OcrResult { text: string, provider: 'vlm'\|'local'\|'none', confidence?: number, chunks?: Array<{index, text}>, warnings: string[] }` |
| 中间产物 2 | 直接作为 F-02 的 `rawText` 进入 `cleanJd → extractJd`（**管线零改动**） |
| 输出（成功） | 与 F-02 相同（`extraction` / `validation` / `level`），外加 `inputMode: 'image'`、`ocr: { provider, confidence }` |
| 输出（失败） | `E_IMAGE_UNSUPPORTED`（格式/体积）、`E_OCR_UNAVAILABLE`（无视觉模型且无本地 OCR）、`E_OCR_EMPTY`（识别为空）、`E_IMAGE_TOO_LONG`（切片后仍超 2 万字） |
| 契约版本 | `ocr-input-v1` |

**关键设计：OCR 只负责"图 → 文本"，不负责"图 → 结构化字段"**

为什么不直接用视觉模型输出 JSON：那会形成**第二条抽取链路**，字段契约、三态截止、技能三属性、K=3 一致性、
校验与待确认都要为图片再实现一遍，评测口径也会分叉。本设计里 OCR 产出的文本立即回到 F-02 的唯一管线，
因此**图片输入与文字输入的抽取质量口径完全一致**（只是多了 OCR 的字符误差）。

### 1.3 分支与变体矩阵（**本节是重点**）

**A. 输入形态**

| 分支 | 判定 | 行为 |
|---|---|---|
| 剪贴板粘贴（`Ctrl+V`） | 编辑器捕获 `paste` 事件的 `image/*` | 最高优先级路径，直接入队 |
| 拖拽文件 | `drop` 事件含图片 | 入队，按拖拽顺序 |
| 文件选择 | `<input type="file" multiple accept="image/*">` | 最多 5 张 |
| 多图 | `images.length > 1` | 按 `order` 依次识别后拼接，图间加 `\n\n` |
| 长截图（高宽比 > 3） | 宽度/高度比判定 | **自动纵向切片**（每片高 ≤ 1600px，**重叠 10%**）→ 逐片识别 → 按重叠区去重拼接 |
| 超长结果 | 拼接后 > 20000 字符 | `E_IMAGE_TOO_LONG`：提示"请裁掉无关部分（招聘 App 的推荐位/广告）" |
| 低分辨率 | 宽度 < 800px | `warnings` 提示"图片偏小可能影响识别"，仍继续 |
| 格式不支持 | 非 png/jpeg/webp | `E_IMAGE_UNSUPPORTED` |
| 体积超限 | 单张 >10MB | `E_IMAGE_UNSUPPORTED` + 提示压缩 |

**B. OCR 引擎选择（降级链）**

| 分支 | 判定 | 行为 | 用户可见 |
|---|---|---|---|
| 视觉模型可用 | `capabilities.vision === true` | **VLM 读图**：prompt 要求"只输出图中文字，保留换行与条目结构，不要解释" | 顶部显示「识别方式：视觉模型（图片会发送至你配置的模型服务）」 |
| 视觉模型调用失败 | 超时 / 不支持 `image_url` / 401 | **降级本地 OCR**（若可用）+ `warnings` | 横幅提示"视觉模型不可用，已改用本地识别" |
| 无视觉模型 + 本地 OCR 可用 | `vision=false` 且本地引擎已加载 | **本地 OCR**（图片**不出机器**） | 「识别方式：本地 OCR（图片未离开本机）」 |
| 两者都不可用 | 无视觉模型 + 本地引擎缺失 | `E_OCR_UNAVAILABLE`：给出**两条可行路径**：① 配一个支持视觉的模型（列出 Qwen-VL / GLM-4V / GPT-4o-mini 示例）；② 手动粘贴文字 | 阻断式提示，而不是报错栈 |
| 识别结果为空 | `text.trim() === ''` | `E_OCR_EMPTY`：提示"没认出文字，请检查图片或改用手动粘贴" | 保留图片供重试 |
| 识别出提示注入 | 复用 F-02 的 `detectPromptInjection` | 与文字输入同等处理（`<jd>` 隔离 + 标记） | "该截图含可疑指令，已隔离处理" |

**C. 隐私与附件**

| 分支 | 行为 |
|---|---|
| 默认 | 有视觉模型时**明确告知**图片会发送到用户配置的服务；无视觉模型时**优先本地** |
| 纯本地开关 | `OCR_MODE=local`：即使有视觉模型也不用，只走本地 OCR |
| PII 检测 | 对 OCR 文本跑 F-02 的 PII 检测（手机号/邮箱/身份证），命中则提示"截图中含个人信息" |
| 图片存档 | 存 `原始JD/attachments/<sha256 前 16 位>.<ext>`；`jobs.jd_structured.source_image` 记相对路径 |
| 删除 | 删除岗位时附件一并删除（`on delete cascade` 语义在应用层实现） |

### 1.4 状态与流转

```
粘贴/拖拽/选择图片
   → 校验（格式/体积/数量）
   → 长图切片
   → OCR（VLM 优先，失败降级本地）
   → 拼接 + 去重
   → cleanJd → extractJd（与文字输入完全相同的路径）
   → 预览 / 校准 / 入库（F-02 的 UI 与 API 全复用）
```

UI 状态机：`idle → hasImages → recognizing（进度：第 n/m 片）→ recognized → 进入 F-02 预览 → saved`

### 1.5 边界与非目标

- **不做**：直接用视觉模型输出结构化 JSON（会分叉抽取链路与评测口径）
- **不做**：手写体识别、印章/水印去除、图片翻译
- **不做**：PDF 截图式解析（扫描版简历/PDF 走 F-06，两者共用 OCR 能力但入口不同）
- **不做**：在服务端保存用户图片超过必要期限（入库后仅保留一份附件）

## 2. 收集需求

### 2.1 需求来源与方法

| 来源 | 结论 |
|---|---|
| 用户需求（2026-10-25） | 招聘网站禁止复制 → 用截图输入 |
| 用户裁决 | 该功能的**补充计划并入 I1.5**，不在 I1 补做 |
| 复用已有裁决 | 隐私（C-10 本地优先）、BYOK（G-12）、降级链（F-01 L0–L4） |

### 2.2 验收场景（Given / When / Then）

- **AC-1 粘贴即用**：Given 一段清晰的招聘 JD 截图，When `Ctrl+V` 后点识别，Then 得到文本并**自动进入解析预览**，字段与文字输入一致。
- **AC-2 多图/长图**：Given 一张手机长截图，When 识别，Then 自动切片拼接，无重复段落、无内容丢失（人工比对首尾句）。
- **AC-3 降级**：Given 视觉模型不可用，When 识别，Then 自动改用本地 OCR（若可用）并显示横幅；若都不可用，Then 给出**两条可执行路径**而非报错。
- **AC-4 隐私提示**：Given 使用视觉模型，Then 界面明示"图片会发送至你配置的模型服务"；Given `OCR_MODE=local`，Then 不调用任何外部服务。
- **AC-5 附件与追溯**：Given 一次截图入库，Then 附件已存 `原始JD/attachments/`，`jd_structured.source_image` 指向它。
- **AC-6 质量门槛**：清晰截图（正文 ≥14px、无遮挡）字符准确率 **VLM ≥95% / 本地 OCR ≥90%**；
  字段抽取准确率相比同内容文字输入**下降 ≤5pt**。
- **AC-7 异常**：非图片/超大/空识别/含 PII/含注入 五种情况各有明确提示，不出现报错栈。

### 2.3 非功能需求

| 项 | 要求 |
|---|---|
| 性能 | 单张（1080px 宽）识别 P95 ≤ 12s；长图切片后 ≤ 30s（含进度提示） |
| 成本 | 视觉模型单张 ≤ ¥0.05（提示截屏裁掉无关区域） |
| 隐私 | 默认不落盘到工作区以外；本地模式图片不出机 |
| 可用性 | 无视觉模型、无本地 OCR 均有明确替代路径 |
| 可访问性 | 粘贴/拖拽/选择三种方式都可用（不强制鼠标） |

### 2.4 优先级（MoSCoW）

- **Must**：粘贴图片、VLM 识别、长图切片、结果进入 F-02 管线、无视觉模型时的明确指引、附件存档。
- **Should**：本地 OCR 兜底、隐私提示、`OCR_MODE=local` 开关、进度显示。
- **Could**：多图拖拽排序、识别失败重试、图片裁剪。
- **Won't**：视觉模型直接出结构化字段、手写体、水印去除。

### 2.5 待澄清问题

| 问题 | 影响 | 默认（未裁决时） |
|---|---|---|
| **本地 OCR 引擎是否引入**（见 §3.4 技术选型） | 依赖体积（WASM 模型 10–40MB）与中文精度 | 先做 **VLM-only**（零新依赖），本地 OCR 作为可选增强 |
| 截图是否默认保存到工作区 | 隐私与可追溯的权衡 | **保存**（用户主动粘贴，且只在本地） |
| 多图上限 5 张是否够用 | 长 JD 可能需要更多 | 5 张（长图切片已覆盖多数场景） |

### 3.4 技术选型（**需裁决**）

| 方案 | 依赖 | 中文精度（经验值） | 隐私 | 成本 | 推荐度 |
|---|---|---|---|---|---|
| **A. 仅 VLM** | 0 新依赖（用户需有视觉模型） | 95%+ | 图片出机 | 按 token 计费 | ⭐ 推荐 MVP |
| **B. VLM + tesseract.js** | +1（WASM ~10MB） | 90–93% | 可全本地 | 免费 | 精度不足时升级 |
| **C. VLM + PaddleOCR-onnx** | +2（模型 20–40MB） | 96%+ | 可全本地 | 免费 | 体积代价大 |
| D. 仅本地 OCR | +1/+2 | 90–96% | 全本地 | 免费 | 无视觉模型用户的唯一选择 |

**建议**：MVP 走 **A**（零新依赖，符合"能省则省"的项目基调），并在 UI 明确提示"需要视觉模型"；
若实际使用中 VLM 识别质量不达标或用户没有视觉模型，再引入 **B**（tesseract.js）作为本地兜底。
C 仅在"必须全离线 + 高精度"时考虑。

### 3.5 风险与回退

| 风险 | 触发信号 | 回退动作 |
|---|---|---|
| 用户的模型不支持视觉 | 首次识别失败 | 自学习标记 + 降级本地/引导配置 |
| VLM 读图乱编内容 | 识别文本与图片人工比对不符 | prompt 加"只抄图、不要补全"，并保留原图供核对 |
| 长图切片重复/丢行 | AC-2 失败 | 增大重叠到 15%，改用"按重叠文本去重"而非固定偏移 |
| 单张成本偏高 | `llm_usage_logs` 显示单张 > ¥0.05 | UI 提示裁掉无关区域 + 压缩到 1080px 宽 |
| 本地 OCR 拖慢首屏 | 包体过大 | 本地引擎按需懒加载（用户点"本地识别"才下载） |

## 4. 如何验收评分

### 4.1 验收清单

- [ ] AC-1 粘贴 → 识别 → 自动进入预览（与文字输入字段一致）
- [ ] AC-2 长截图切片拼接无重复、无丢失
- [ ] AC-3 三级降级链可用（VLM → 本地 → 明确指引）
- [ ] AC-4 隐私提示与 `OCR_MODE=local` 生效
- [ ] AC-5 附件存档 + `source_image` 可追溯
- [ ] AC-6 字符准确率（VLM ≥95% / 本地 ≥90%）+ 字段准确率下降 ≤5pt
- [ ] AC-7 五类异常均有可操作提示
- [ ] 适配层 `vision` 能力标记正确（预设表 + 失败自学习）

### 4.2 评分卡（100 分）

| 维度 | 权重 | 判据 |
|---|---|---|
| 识别质量 | 30 | AC-6 达标；长图拼接正确 |
| 降级完整性 | 25 | AC-3 三级链路 + 无报错栈 |
| 隐私与安全 | 15 | AC-4 + PII 提示 + 附件不出机（本地模式） |
| 体验 | 15 | 粘贴即用、有进度、识别后可改、失败可重试 |
| 工程规范 | 15 | 测试覆盖、适配层向后兼容、typecheck/lint 0 |

### 4.3 通过阈值

| 分数 | 结论 |
|---|---|
| ≥85 | 通过（红线：图片在本地模式下外发、识别内容与图严重不符、崩溃 → 任一即不通过） |
| 70–84 | 有条件通过，扣分项列入 F-03 之后 |
| <70 | 不通过，回到 T2 重做 OCR 编排 |

## 6. 多模型路由（2026-10-25 扩展，Q-09 = A 之后的实现方式）

**需求**：文本模型与视觉模型分开配置——"需要图像模型的时候就调用图像模型"。
现实动机：日常抽取用便宜的快模型、偶尔读图用视觉模型，两者性价比结构不同。
（2026-10 复核：DeepSeek `deepseek-flash` 已支持 Vision，因此"单 Key 全包"也成为可行方案，见 decisions_log §18）
一套配置逼用户在"便宜"和"能读图"之间二选一，不合理。

### 6.1 配置契约（`LLM_*` 与 `LLM_VISION_*` 两组独立配置）

| 键 | 作用 | 留空时 |
|---|---|---|
| `LLM_PROVIDER` / `LLM_API_KEY` / `LLM_MODEL` / `LLM_BASE_URL` | **文本 profile**：抽取、生成、校验 | `LLM_PROVIDER` 默认 `deepseek` |
| `LLM_VISION_PROVIDER` | **视觉 profile**：截图识别 | **未配置 → 截图识别不可用**（文本功能不受影响） |
| `LLM_VISION_MODEL` | 视觉模型名 | 用该 provider 默认模型（**建议显式写** `qwen-vl-plus` 等） |
| `LLM_VISION_API_KEY` | 独立 Key | 继承 `LLM_API_KEY`（同一家服务商时可省略） |
| `LLM_VISION_BASE_URL` | 独立地址（中转站 / 自建网关） | 用 provider 内置地址 |

**向后兼容**：不配置 `LLM_VISION_PROVIDER` 时行为与改造前一致；截图入口给出"未配置视觉模型"的可操作提示。

### 6.2 路由规则

```
/api/parse-jd  → router.text    （文本 profile，原有逻辑）
/api/ocr       → router.vision  （视觉 profile；未配置或配置非法时返回可操作错误）
doctor         → 两行：文本 / 视觉（含"视觉 ✓/✗"判定）
```

- 视觉 profile 的 env 是**派生**的（override provider/baseUrl/model/key），因此复用 F-01 全套适配层：
  出站白名单、私网保护、重试、用量记账、降级链都不需要重写；
- 派生时**清空任务级模型覆盖**（`LLM_MODEL_EXTRACT/GENERATE`），避免把文本模型套到图片上；
- 视觉 profile 创建失败（未知 provider / custom 缺 baseUrl / 私网未开）**不抛 500**，
  折成 `info.vision.reason` 由 API 返回可操作提示。

### 6.3 失败与降级

| 情况 | 行为 |
|---|---|
| 未配置视觉模型 | `E_OCR_UNAVAILABLE`：给出要加的三行 `.env` + 候选视觉模型列表 |
| 配了但不是视觉模型（如 `qwen-plus`） | `E_OCR_UNSUPPORTED_MODEL`：报出当前模型名 + 建议模型；**不偷偷降级成文本模型** |
| 视觉模型调用被拒（不支持多模态） | `E_OCR_UNSUPPORTED_MODEL`（同义归并） |
| 视觉模型超时/网络错误 | `E_OCR_FAILED` + 排查建议；用户仍可手动粘贴文字 |
| 文本模型不可用 | 与截图无关：截图识别仍可用（两者独立） |

### 6.4 架构取向（为 F-07 留口）

对外是**两个命名 profile**（`text` / `vision`），对内是通用 `createModelRouter(env)`：
等 F-07（BYOK 设置页，I2）落地，`user_llm_credentials` 表里的任意多条凭证都可作为额外 profile
接进同一个 router，调用方（`/api/ocr`、`/api/parse-jd`）无需改动。

**测试**：`tests/model-router.test.ts` 12 例（解析/脱敏/继承/非法配置/派生 env/摘要）。

**未做**：N 个任意 profile 的 UI 与持久化（属 F-07，4h）；本轮只做两组 env 配置。
