**一句话定义**：把你做过的实习、项目、科研、社团，整理成"情境-任务-行动-结果"四段可复用的结构化资产。

> 为什么它是核心：后续的匹配（I5）与材料生成（I6）都要从经历库里"取事实"。
> 经历库不结构化，生成的简历就是空话；这也是 mission 里"两个库"的另一半。

## 1. 功能规格与分支

### 1.1 用户故事

- **US-1**：作为求职者，我希望手动填一段经历，系统提示我按 STAR 补齐缺的部分，以便写得比记忆里更完整。
- **US-2**：作为求职者，我希望粘贴一大段自述（"我在 XX 公司做后端，负责订单系统……"），
  系统自动拆成结构化四段，我改改就能用。
- **US-3**：作为求职者，我希望经历里的技能标签能归一（"JS"/"JavaScript" 算一个），
  以便后续与岗位技能做匹配。
- **US-4**：作为求职者，我希望删掉一段经历后还能恢复，以便误删不心疼。

### 1.2 输入 / 输出契约

| 项 | 内容 |
|---|---|
| 输入（表单） | `ExperienceForm { type, org, role, startDate, endDate?, summary, star: {situation,task,action,result}, skills[], metrics[], evidenceUrls[] }` |
| 输入（自由文本） | `FreeTextExperience { rawText: string }`，长度 20–8000 字符 |
| 中间产物 | `StructuredExperience`（同表单结构 + `evidence: Record<字段, 原文片段>` + `confidence`） |
| 输出 | `experiences` 行（0001 已建表）+ `skills` 经 C-07 词表归一 |
| 错误码 | `E_EMPTY`、`E_TOO_LONG`、`E_DATE_RANGE`（结束早于开始）、`E_NO_CREDENTIAL`（→ 手动模板，非报错）、`E_DUPLICATE` |
| 契约版本 | `experience-v1` |

### 1.3 分支与变体矩阵

| 分支 | 条件 | 行为 |
|---|---|---|
| 纯手动 | 用户直接填表 | 表单校验（必填：type/org/summary；日期区间合法） |
| 自由文本 → STAR | 有模型 | LLM 拆四段 + 抽 skills/metrics，**逐段可编辑**，全部标"待确认" |
| 自由文本 → STAR（无 Key） | 无凭证 | 显示空 STAR 模板 + 把原文放进 `raw_text` 供参考，不伪造内容 |
| 文本过短 | <20 字符 | `E_EMPTY` 提示补充 |
| 时间区间非法 | `endDate < startDate` | `E_DATE_RANGE`，表单内联报错 |
| 量化指标识别 | 文本含"提升 30%""覆盖 200 万用户" | 抽 `metrics: [{metric, value, unit, direction}]`；无法判断单位则留空但保留原文 |
| 技能归一 | skills 命中 C-07 词表 | 归一（`JS`→`JavaScript`）；未命中 → `pending_review` |
| 重复录入 | 同 `org` + 同 `role` + 同起始月 | `E_DUPLICATE`：提示"看起来与已有经历重复"，给"查看已有 / 仍要新建" |
| 删除 | 用户删除 | **软删**（`deleted_at`），回收站后置（C-01）；恢复接口保留 |
| 超长自由文本 | >8000 | 分段抽取后合并（复用 F-02 的分段思路） |

### 1.4 状态与流转

`draft（新建/编辑中） → saved（入库） → deleted（软删，可恢复）`

- STAR 四段允许"部分为空"，但 `action` 与 `result` 至少各有一句才允许标记为"可用于生成简历"
- 任何字段修改都更新 `updated_at`

### 1.5 边界与非目标

- **不做**：自动编造量化数据（没有就留空，不许算个"提升 30%"）
- **不做**：经历版本管理（P3 的 E-05 范围）
- **不做**：从社交媒体自动抓取经历

## 2. 收集需求

### 2.1 需求来源与方法

| 来源 | 结论 |
|---|---|
| mission（两个库） | 经历库与岗位库并列核心 |
| tech_stack §9.2 `experiences` 表 | 字段已定（STAR 四段 + skills + metrics + evidence_urls） |
| C-01 裁决 | 回收站后置，先用软删 |
| C-07 裁决 | 技能词表归一 + 未命中进待审 |

### 2.2 验收场景

- **AC-1 手动录入**：填一段完整经历并保存，列表可见、详情可读。
- **AC-2 自由文本 → STAR**：粘贴一段自述，得到四段结构与 skills，**每段可编辑**，未确认内容标"待确认"。
- **AC-3 技能归一**：`JS`→`JavaScript`；未命中词表的新词进待审。
- **AC-4 量化指标**：`提升 30%` → `{value:30, unit:'%'}`；无单位的数字不强行补。
- **AC-5 重复检测**：同 org+role+起始月 再次录入 → 提示重复 + 三个选项。
- **AC-6 恢复**：删除后可通过接口/界面恢复。
- **AC-7 无 Key 可用**：无凭证时显示模板而非报错。

### 2.3 非功能需求

| 项 | 要求 |
|---|---|
| 性能 | 自由文本抽取 P95 ≤ 8s；表单保存 ≤ 500ms |
| 隐私 | 经历原文不出本机（仅发往用户配置的模型） |
| 可用性 | 无 Key 时手动路径完整可用 |

### 2.4 优先级（MoSCoW）

- **Must**：表单录入、自由文本→STAR、技能归一、软删、重复检测、校验。
- **Should**：量化指标抽取、evidence 片段、待确认标记。
- **Could**：批量导入（多段一次录入）、经历排序拖拽。
- **Won't**：版本管理、社媒抓取。

### 2.5 待澄清问题

| 问题 | 影响 | 默认 |
|---|---|---|
| STAR 四段是否强制全填？ | 录入体验 | **不强制**；但 `action`+`result` 决定能否用于生成 |
| 经历是否记录时间精度到"日"？ | 排序与年限计算 | 到**月**即可（`date` 存月初） |

## 4. 如何验收评分

### 4.1 验收清单

- [ ] AC-1~AC-7 全过
- [ ] 10 段经历录入完成，STAR 四段完整率 ≥80%
- [ ] 自由文本→STAR 的字段准确率 ≥80%（人工比对 5 段）
- [ ] 技能归一正确率 ≥90%
- [ ] 无凭证时手动路径可用

### 4.2 评分卡（100 分）

| 维度 | 权重 | 判据 |
|---|---|---|
| 录入体验 | 25 | 表单可用、校验明确、无 Key 也能录 |
| STAR 结构化质量 | 30 | AC-2 准确率达标、逐段可编辑、不编造 |
| 数据质量 | 20 | 技能归一、指标抽取、重复检测 |
| 可恢复性 | 10 | 软删/恢复可用 |
| 工程规范 | 15 | 测试、typecheck/lint 0、文档 |

### 4.3 通过阈值

≥85 通过；70–84 有条件通过；<70 不通过。
**红线**：编造量化数据、原文泄漏、误删不可恢复 → 任一即不通过。
