## 1. 功能规格与分支

### 1.1 用户故事

- **US-1**：作为求职者，我希望拖入一份 PDF 简历，系统列出识别到的 3–5 段经历，我改改就能入库。
- **US-2**：作为求职者，我希望系统**不要自动全收**——识别错的内容进库比没进更糟。
- **US-3**：作为求职者，如果我的简历是扫描件（没有文字层），我希望系统告诉我"需要 OCR 或手动录入"，而不是给一堆乱码。

### 1.2 输入 / 输出契约

| 项 | 内容 |
|---|---|
| 输入 | `ResumeFile { data: Uint8Array, mime: 'application/pdf'\|'application/vnd.openxmlformats-officedocument.wordprocessingml.document', size ≤10MB }` |
| 中间产物 1 | `ExtractedText { text: string, pageCount?: number, hasTextLayer: boolean, warnings: string[] }` |
| 中间产物 2 | `CandidateExperience[]`（复用 F-05 的 `StructuredExperience` + `evidence`） |
| 输出 | 候选列表 → 用户逐条"确认入库 / 编辑后入库 / 丢弃" |
| 错误码 | `E_UNSUPPORTED_FORMAT`、`E_TOO_LARGE`、`E_NO_TEXT_LAYER`（扫描件）、`E_PARSE_FAILED`、`E_NO_EXPERIENCE`（没识别出经历） |
| 契约版本 | `resume-import-v1` |

### 1.3 分支与变体矩阵

| 分支 | 判定 | 行为 |
|---|---|---|
| 文字层 PDF | 抽取文本长度 > 100 字符 | 正常解析 |
| **扫描版 PDF** | 抽取文本 ≈ 空 | `E_NO_TEXT_LAYER`：提示"这是扫描件，可用截图 OCR（F-04）或手动录入"，**不输出乱码** |
| DOCX | mime 命中 | `mammoth` 转文本（保留段落/列表结构） |
| 双栏版式 | 文本出现大量交错短行 | 按"块级元素 + 列间距"重排后解析；解析质量差时提示手动 |
| 表格型简历 | 文本里出现 ` | ` 分隔 | 保留表格行为 ` | ` 行，交给抽取 |
| 多段经历 | 识别到 ≥2 个"公司/时间"锚点 | 输出候选列表（每段一条），**不自动入库** |
| 零经历 | 没识别到任何经历锚点 | `E_NO_EXPERIENCE`：提示手动录入（不猜） |
| 页眉页脚/水印 | 重复出现 ≥3 次的短行 | 自动剔除 |
| 超长简历 | >10 页 | 只解析前 10 页 + 提示 |
| 已有相同经历 | 与经历库指纹重复 | 候选上标"已存在"，默认不勾选 |

### 1.4 状态与流转

`uploaded → parsing → candidates（逐条核对）→ imported（部分/全部）`

- **绝不自动入库**：每条候选都必须经过确认（这是本功能最重要的设计约束）

### 1.5 边界与非目标

- **不做**：扫描件直接 OCR（复用 F-04，不自建第二套 OCR）
- **不做**：简历排版还原（不需要还原成"好看的简历"）
- **不做**：PDF 加密文件破解（直接报 `E_PARSE_FAILED`）

## 2. 收集需求

### 2.1 需求来源与方法

| 来源 | 结论 |
|---|---|
| 用户批注 A-05（logs/README A11） | 简历解析进入 **P1**；Node 端实现，不引入 Python |
| mission | 旧简历是经历库的"冷启动入口" |
| F-05 设计 | 候选结构复用 `StructuredExperience` |

### 2.2 验收场景

- **AC-1 正常导入**：一份 2 页文字层 PDF → 识别 ≥3 段候选 → 逐条确认后入库。
- **AC-2 扫描件**：无文字层 → `E_NO_TEXT_LAYER` + 两条可行路径（OCR / 手动），不输出乱码。
- **AC-3 不自动入库**：解析完成但用户不确认 → 经历库条数不变。
- **AC-4 DOCX**：同样能识别 ≥3 段。
- **AC-5 重复**：导入已在库的经历 → 候选标"已存在"、默认不勾选。
- **AC-6 可编辑**：候选可修改后再入库（与 F-05 共用表单）。

### 2.3 非功能需求

| 项 | 要求 |
|---|---|
| 性能 | 10 页 PDF 解析 P95 ≤ 8s |
| 隐私 | 文件只在本地解析，**不上传**（除非用户显式选择用模型辅助切分） |
| 依赖 | `unpdf`（或 `pdfjs-dist`）+ `mammoth`，均为纯 JS、无需 Python/系统库 |

### 2.4 优先级（MoSCoW）

- **Must**：文字层 PDF、DOCX、候选列表、逐条确认、扫描件明确提示。
- **Should**：页眉页脚剔除、重复标记、编辑后入库。
- **Could**：多文件批量导入。
- **Won't**：扫描件直接 OCR、版式还原、加密 PDF。

### 2.5 待澄清问题

| 问题 | 影响 | 默认 |
|---|---|---|
| 解析是否调用模型辅助切分经历？ | 成本与隐私 | **先纯规则切分**（公司/时间锚点），质量不足再引入模型 |
| 是否保留原简历文件？ | 追溯与隐私 | 保留在 `原始JD/attachments/` 同级目录（可删） |

## 4. 如何验收评分

### 4.1 验收清单

- [ ] AC-1~AC-6 全过
- [ ] 3 份真实简历（PDF 文字层 / DOCX / 扫描件）各走一遍
- [ ] 扫描件给出可操作提示（不输出乱码）
- [ ] 解析后经历库条数不变（未确认不入库）

### 4.2 评分卡（100 分）

| 维度 | 权重 | 判据 |
|---|---|---|
| 解析质量 | 30 | 3 份简历均识别 ≥3 段且内容正确 |
| 安全与克制 | 25 | 不自动入库、不编造、隐私不外传 |
| 体验 | 20 | 候选可编辑、重复可辨、失败有路径 |
| 依赖与性能 | 10 | 纯 JS 解析、P95 ≤8s |
| 工程规范 | 15 | 测试、typecheck/lint 0 |

### 4.3 通过阈值

≥85 通过。**红线**：未确认即入库、输出乱码当结果、文件外传 → 任一即不通过。
