# ADR-0007：BYOK 与 Provider 适配层设计

- 状态：已采纳（G-12 裁决 + I0 实施）
- 日期：2026-10-15（裁决）/ 2026-10-16（I0 实施）
- 关联：F-01（T4/T5/T6）、[tech_stack.md](../../spec/tech_stack.md) §3.3、§3.9

## 背景

用户要求"上线 GitHub 后允许使用者自己选择大模型 API"。本地优先（ADR-0003）意味着**作者不提供模型额度**，
因此"用户能自己配上一个可用的模型"是产品能否被用起来的前提，而不是可选增强。

同时必须避免两件事：① 业务代码被某个厂商 SDK 绑死；② 用户拿本项目当任意 LLM 代理（SSRF / 滥用）。

## 选项

| 维度 | 选项 | 取舍 |
|---|---|---|
| 接入协议 | 各厂商原生 SDK / **统一 OpenAI 兼容端点（采纳）** | 原生 SDK 表达力强但绑死厂商；兼容端点覆盖面广、零依赖 |
| 适配层位置 | 业务代码内联调用 / **独立 `src/lib/llm` + 注册表（采纳）** | 内联最省事但红线无法守住 |
| 自定义端点 | 全部开放 / **本地模式开放、展示页不开放（采纳）** | 全开放便于用中转站，但展示页有被当代理的风险 |
| 密钥存储 | 明文 / 环境变量 / **AES-256-GCM 密文 + 只写不回读（采纳）** | 密文 + 不回读同时满足可用性与安全 |
| 能力探测 | 不探测，失败再说 / **探测 + 24h 缓存 + 调用中自学习（采纳）** | 探测一次可避免"到用的时候才炸" |

## 决定

1. **统一 OpenAI 兼容协议**：`/chat/completions` 与 `/embeddings`，注册表内置 7 个预设 + `custom`；
   新增 provider = 改注册表一行（AC-13）。
2. **零运行时依赖**：适配层只用全局 `fetch`，因此可在无网络环境用桩测试；厂商 SDK 名单在
   ESLint 与 `scripts/check-adapter-purity.mjs` 双重拦截（红线③）。
3. **错误分类驱动降级**：401/403→auth、429→rate_limit（读 `Retry-After`）、5xx→server、
   网络/超时→unreachable、400/404/422→config；降级链 L0–L4 据此分流。
4. **结构化输出双路径**：tool calling 优先 → Prompt-JSON + 校验 + 修复重试 ≤2；
   上游明确拒绝 tools 时**就地自学习降级**并记住该能力。
5. **安全边界**：私网地址默认拒绝（`ALLOW_PRIVATE_BASE_URL` 才放行）；出站白名单只放行用户配置域名
   （`EGRESS_EXTRA_HOSTS` 可扩展）；密钥密文存储 + 日志/遥测脱敏（7 类密钥形态）。
6. **无密钥可用**：L4 规则模式，不报错、有引导——这是"装上就能用"的底线。

## 后果

- ✅ AC-3（换模型只改 `.env`）、AC-4（保存阶段校验 Key）、AC-5（不可达提示）、AC-8（私网保护）、
  AC-9（密钥不回读）、AC-10（出站白名单）、AC-13（零厂商 SDK）均有对应用例覆盖。
- ✅ 可测试性大幅提升：依赖（fetch / sleep / now / guard）全部注入，126 个用例无需网络。
- ⚠️ Prompt-JSON 路径的稳定性依赖模型的指令遵循能力；对弱模型需要靠修复重试兜底（已实现 ≤2 次）。
- ⚠️ 各厂商"是否支持 tool calling / json_schema"的判定依赖预设表 + 探测 + 调用中自学习三层，
  预设表可能随后续厂商调整而过时——维护点为 `src/lib/llm/registry.ts`。
- 待验证：真实网络下对 7 个预设 provider 的逐一冒烟（当前环境无网络），已列入 F-01 的 Provider 兼容性测试。
