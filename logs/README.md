## 2. 术语约定（唯一口径）

| 术语 | 含义 | 时间范围 |
|---|---|---|
| **MVP** | P0–P1，必须做 | 第 1–3 周（截至 11/02） |
| **Demo 版** | P0–P2，5 周内交付的完整范围 | 第 1–5 周（10/13–11/16） |
| **Post-MVP** | P3–P5，排期待定 | 11/16 之后 |
| **过程门** | 阶段内的验证阈值，未达标可继续但要记录风险 | 第 1 周末 80%、第 4 周 80% |
| **最终验收** | 对外口径的指标要求 | 抽取 90%、匹配一致 85% |

> ⚠️ `mission.md` / `tech_stack.md` 中的 `P0–P5` 在**功能优先级**语境下与上述"MVP/Demo 版"对应；在**项目阶段**语境下是阶段号。两者通过本文第 4 节的对照表映射。
> ⚠️ **两个"Demo"要区分**：**Demo 版** = P0–P2 的交付范围（时间维度）；**在线展示页**（无状态只读站点）= C-10 的产物，不落库、不注册，只用于给面试官点开看。

## 5. 容量与节奏原则（E-01 / E-02 用户批注）

用户批注原文：**"时间不用限制的太死板，可以调整时间计划，但不要将工期框的太死。"**

对应执行口径（已随"功能增量驱动"改版落地，见 `roadmap.md` §0–§1、§5）：

1. **按功能增量交付，不按日期交付**：进度 = `已验收功能项 / 该增量功能项总数`。
2. 日期只承担两个作用：**总容量预算**（35 天 ≈ 190–220 小时）与**里程碑软锚点**。
3. 允许增量整体前移或后移（相邻增量之间借用容量），但**不新增范围**。
4. 任一增量实际耗时超过估算 30% 时，启动降级链（I7 → 跟进建议 → 面试题 → 雷达图 → 匹配 → 话术），而不是挤压发布增量。
5. `roadmap.md` 的"参考窗口"列仅用于容量校准，**不构成承诺**。
