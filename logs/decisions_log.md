### 12.3 R1-03 引发的设计面（本次新增）

用户一句"允许用户修改"使工作区从"导出视图"升级为**第二编辑面**，必须补齐：

- **列级权限**：同步键只读 / 抽取字段可改（= 人工校准）/ 用户字段可改 / 计算字段只读 / 未知新列保留；

- **格式漂移容忍**：Excel 会改写日期/数字/去 BOM/插入列，解析须按表头名匹配、多格式日期解析、忽略未知列；

### 13.3 关键设计取舍

1. **三态而非"必填/空"两态**：`text_only`（"招满为止"）与 `absent`（完全没提）要分开——
   前者有价值信息（可显示"原文：招满为止"），后者说明 JD 缺失，两者都不该阻塞入库。
2. **熟练度与必需性正交**：JD 里"熟悉 K8s 优先"= 加分 + 熟悉，"必须具备 Go"= 必须 + 未标注熟练度。
   合并成一个"难度等级"会丢失信息。
3. **熟练度必须可追溯**：每行技能带 `basis_phrase`（原文短语），没有就记 `unknown` 而不是猜。
   这是"幻觉抑制"原则（tech_stack §5）在技能维度上的延伸。
4. **差距分析依赖"我的水平"**：I1 阶段没有经历库（F-03 在 I2），因此需要 `我的技能.csv` 自评作为唯一输入；

**关键技术事实（必须记住）**：**CSV 无法保存单元格颜色**。先裁"用 CSV"，后提"要颜色"，二者在纯 CSV 下不可兼得。
最终裁决不是加 XLSX，而是**分列**——同一份 CSV 里用不同列承载"明确·必须 / 明确·加分 / 推测"，
既保留零依赖与单一数据源，又满足"一眼可区分 + 可按列筛选排序"。

**为什么"分列"优于此前的两种方案**：

| 方案 | 依赖 | 文件数 | 可编辑 | 可筛选 |
|---|---|---|---|---|
| CSV + 单元格颜色 | 不可能（纯文本） | — | — | — |
| CSV + XLSX 着色视图 | +1（exceljs） | +1 重复表 | 需分别维护 | 有限 |
| **CSV 分列（采纳）** | **0** | **不变** | ✅ | ✅ 列级筛选/排序 |

**容量缺口**：I1 44h 使总工时达 **214h**，超 200h 预算 14h。已在 `roadmap.md` §5 列出三种方案，

不是"入库闭环"的必要条件。待用户拍板。

### 14.2 ⚠️ 算术纠正（我上一轮的方案表有错）

上一轮在 `roadmap.md §5` 写"P1：214h → 200h，预算刚好"——**这是错的**。
把工作从一个增量搬到另一个增量**不改变总工时**：搬走 10h 只让 I1 变小，总量不变。

**正确账目**：

```
原计划：I1 = 30h，总量 200h
新增保留：R3 (1h) + R4/R5 (3h) = +4h → I1 = 34h
移出 5 周计划：R1 工作区 10h（不计入 5 周总量）
∴ 5 周内总量 = 200 + 4 = 204h，仍超预算 4h（+2%）
```

**4h 缺口的收口方式（本次采用 A，可随时改）**：

| 方案 | 动作 | 结果 |
|---|---|---|
| **A（采用）** | 接受 **204h**（+2%），不裁功能 | 与 200h 软预算偏差在可接受范围；I7 保持 6h 最小提醒不变 |
| B | 从 I7 再让 4h（6h → 2h） | 204h → 200h，但提醒能力只剩"截止 T-1 单渠道"的骨架 |
| C | 把 R4/R5（3h）也移出 I1 | I1 = 31h，总量 201h；但"技能只有名字没有属性"会让 I1 的抽取质量无法验收 |

采用 A 的理由：4h ≈ 2% 偏差小于"重排一遍里程碑"的成本，且 I7 已是最小版，再砍会让"提醒"这条产品线彻底消失。
