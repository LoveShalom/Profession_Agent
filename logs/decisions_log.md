### 12.3 R1-03 引发的设计面（本次新增）

用户一句"允许用户修改"使工作区从"导出视图"升级为**第二编辑面**，必须补齐：

- **列级权限**：同步键只读 / 抽取字段可改（= 人工校准）/ 用户字段可改 / 计算字段只读 / 未知新列保留；

### 13.3 关键设计取舍

1. **三态而非"必填/空"两态**：`text_only`（"招满为止"）与 `absent`（完全没提）要分开——

2. **熟练度与必需性正交**：JD 里"熟悉 K8s 优先"= 加分 + 熟悉，"必须具备 Go"= 必须 + 未标注熟练度。
   合并成一个"难度等级"会丢失信息。
3. **熟练度必须可追溯**：每行技能带 `basis_phrase`（原文短语），没有就记 `unknown` 而不是猜。
   这是"幻觉抑制"原则（tech_stack §5）在技能维度上的延伸。
4. **差距分析依赖"我的水平"**：I1 阶段没有经历库（F-03 在 I2），因此需要 `我的技能.csv` 自评作为唯一输入；

**关键技术事实（必须记住）**：**CSV 无法保存单元格颜色**。先裁"用 CSV"，后提"要颜色"，二者在纯 CSV 下不可兼得。
最终裁决不是加 XLSX，而是**分列**——同一份 CSV 里用不同列承载"明确·必须 / 明确·加分 / 推测"，
既保留零依赖与单一数据源，又满足"一眼可区分 + 可按列筛选排序"。

**为什么"分列"优于此前的两种方案**：

| 方案 | 依赖 | 文件数 | 可编辑 | 可筛选 |
|---|---|---|---|---|
| CSV + 单元格颜色 | 不可能（纯文本） | — | — | — |
| CSV + XLSX 着色视图 | +1（exceljs） | +1 重复表 | 需分别维护 | 有限 |
| **CSV 分列（采纳）** | **0** | **不变** | ✅ | ✅ 列级筛选/排序 |

**容量缺口**：I1 44h 使总工时达 **214h**，超 200h 预算 14h。已在 `roadmap.md` §5 列出三种方案，

不是"入库闭环"的必要条件。待用户拍板。

## 17. 第十七轮：多模型路由（文本 / 视觉分开配）（2026-10-25）

### 17.1 需求

> "可不可以改成支持多个API的模式，需要图像模型的时候就调用图像模型。"

> ⚠️ 2026-10-25 复核：DeepSeek `deepseek-flash`（V4.1-Flash）**已支持 Vision**（官方定价页 Vision ✓）。
> 因此"DeepSeek 没有视觉模型"的前提已不成立，`supportsVision` 已更新为识别 `deepseek-flash`；
> 价格与选型见 §18。

**动机（也是设计依据）**：文本模型与视觉模型的性价比结构不同。
日常抽取要便宜快、读图要视觉能力，两者单价差一个量级。
一套配置逼用户在"便宜"和"能读图"之间二选一——这是配置缺陷，不是功能缺陷。

### 17.2 方案（采用：两组 env 配置 + 内部通用 router）

| 组 | 键 | 用途 | 留空行为 |
|---|---|---|---|
| 文本 | `LLM_PROVIDER` / `LLM_API_KEY` / `LLM_MODEL` / `LLM_BASE_URL` / `LLM_MODEL_EXTRACT` / `LLM_MODEL_GENERATE` | 抽取、生成、校验 | `LLM_PROVIDER` 默认 `deepseek` |
| 视觉 | `LLM_VISION_PROVIDER` / `LLM_VISION_MODEL` / `LLM_VISION_API_KEY` / `LLM_VISION_BASE_URL` | 截图识别（`/api/ocr`） | **未配置 = 截图识别不可用**，文本功能不受影响 |

**关键实现取舍**

| 取舍 | 理由 |
|---|---|
| 视觉 env **派生**自文本 env（override provider/baseUrl/model/key） | 直接复用 F-01 全套适配层：出站白名单、私网保护、重试、用量记账、降级链**零重写** |
| 派生时清空 `LLM_MODEL_EXTRACT/GENERATE` | 否则任务级模型覆盖会把**文本模型名**套到图片请求上（很隐蔽的 bug） |
| `LLM_VISION_API_KEY` 留空继承 `LLM_API_KEY` | 同一家服务商（如都用 Qwen）只需填模型名，少一处密钥管理 |
| 视觉 profile 创建失败**不抛 500** | 折成 `info.vision.reason`，API 返回可操作提示（未知 provider / custom 缺 baseUrl / 私网未开） |
| **不偷偷降级**到文本模型 | 文本模型读不了图，静默降级会得到"识别为空"这种假故障；必须明确报"当前模型不支持读图"并给候选模型 |
| 对外 2 个命名 profile，对内 `createModelRouter(env)` | 等 F-07（BYOK 设置页）落地，`user_llm_credentials` 的任意多条凭证可接进同一个 router，调用方不改代码 |

### 17.3 不做什么（防止范围膨胀）

- **不做 N 个任意 profile 的 UI 与持久化**：属 **F-07 BYOK 设置页（I2，4h）**；本轮只做两组 env
- **不做按任务自动选模型**（如"生成用强模型"）：已有的 `LLM_MODEL_EXTRACT/GENERATE` 已覆盖
- **不做视觉模型失败后自动换另一个视觉模型**：需要凭证池，属 F-07 之后
- **不引入本地 OCR**：Q-09 已裁决 A，保持不变

### 19.2 ⚠️ 实测发现：同 Key 下 deepseek-flash 不适合做文本抽取

## 38. 第三十八轮：PowerShell 脚本编码 bug（用户实跑发现）（2026-11-15）

### 38.1 现象

用户运行 `npm run shortcut` 报：

```
所在位置 scripts/make-shortcut.ps1:19 字符: 27
+ $shortcut.IconLocation = 'C:\Windows\System32\shell32.dll,21'
表达式或语句中包含意外的标记"C:\Windows\System32\shell32.dll"
字符串缺少终止符: '。
```

### 38.2 根因

**Windows PowerShell 5.1 读取 `.ps1` 时：无 BOM 的文件按系统 ANSI 代码页（zh-CN = GBK）解码**。
我生成的脚本是 UTF-8 无 BOM，中文注释/提示被错误解码，字节序列吃掉了引号 → 解析器报"字符串缺少终止符"。
与脚本逻辑无关，纯编码问题。

### 38.3 修法（三层）

| 层 | 做法 |
|---|---|
| 脚本 | `scripts/make-shortcut.ps1`、`scripts/install-autostart.ps1` 改为**纯 ASCII**（英文注释与提示，0 个非 ASCII 字节） |
| 验证 | 用 `[System.Management.Automation.Language.Parser]::ParseFile` 静态验证语法 + 统计非 ASCII 字节数 |
| 文档 | 故障表与部署文档补这条坑；并约定"今后 `.ps1` 一律 ASCII（或 UTF-8 with BOM）" |

### 38.4 横向检查

| 文件类型 | 风险 | 处理 |
|---|---|---|
| `.ps1` | **高**（PS 5.1 按 ANSI 读） | 已全部改 ASCII |
| `.bat` | 中（cmd 按控制台代码页显示，乱码但不报错） | 加 `chcp 65001 >nul` |
| `.mjs` / `.ts` | 低（Node 固定 UTF-8） | 无需处理 |
| `.md` / `.json` | 低 | 无需处理 |

### 38.5 教训

这类"只在我机器上炸"的问题，根因是**工具链默认编码假设不同**：Node 假设 UTF-8、PowerShell 5.1 假设 ANSI、cmd 假设控制台代码页。
跨工具链分发的脚本，**要么纯 ASCII，要么显式声明编码（BOM）**。已在文档里固化为约定。

## 39. 第三十九轮：cmd 批处理编码陷阱（用户双击 start.bat 失败）（2026-11-15）

### 39.1 现象

双击 `start.bat` 后窗口里出现一堆"不是内部或外部命令"的碎片：

```
'own' 不是内部或外部命令…
'vel' 不是内部或外部命令…
'细https:' 不是内部或外部命令…
'ession' 不是内部或外部命令…
'---------------' 不是内部或外部命令…
请按任意键继续. . .
```

### 39.2 根因（两层叠加）

| 层 | 问题 | 说明 |
|---|---|---|
| 1 | `.bat` 含中文且无 BOM | cmd 按控制台代码页（zh-CN=GBK）逐字节解析 UTF-8 中文 → 字节被误解码，行首 `echo`/`REM` 被吃掉，后半截当命令执行 |
| 2 | **文件中间 `chcp 65001`** | cmd 解析批处理时按"读取时的代码页"分块读；**中途切换代码页会让文件指针错位**（cmd 老 bug），后续行被截断拼接 |

`own` ← `docker compose down`；`细https:` ← `https://nodejs.org` 前的中文字节；`---------------` ← 原分隔线。

### 39.3 修法

| 项 | 做法 |
|---|---|
| 编码 | `start.bat` 重写为**纯 ASCII**（英文提示，0 个非 ASCII 字节） |
| 换行 | **CRLF**（38 行 CRLF，0 行 LF-only） |
| chcp | 保留 `chcp 65001 >nul`，但**只有在文件纯 ASCII 时才安全**（ASCII 字节在 65001/936 下一致） |
| 结构 | 用 `goto :label` 替代多行 `if (...)` 块，减少解析歧义 |
| 校验 | 脚本自动检查：非 ASCII=0、无 BOM、LF-only=0 |

### 39.4 固化为项目约定

| 文件类型 | 硬性要求 |
|---|---|
| `.bat` | **纯 ASCII + CRLF**；需要中文提示时在 README 里写，不要写进 bat |
| `.ps1` | **纯 ASCII**（或 UTF-8 with BOM）；PowerShell 5.1 按 ANSI 读无 BOM 文件 |
| `.mjs` / `.ts` | UTF-8 即可（Node 固定 UTF-8） |

教训：**在 Windows 上分发脚本，"让终端显示中文"和"让解析器不崩"是两件事**；先保证 ASCII，再谈中文提示。

## 43. 第四十三轮：启动器"构建过期"缺陷（用户看不到删除按钮）（2026-11-15）

### 43.1 现象

用户按验收指南找「删除」按钮，但 `/jobs` 列表里没有。

### 43.2 根因

`scripts/local-start.mjs` 的构建判断是 **"`.next/BUILD_ID` 存在就跳过构建"**：

```
.next/BUILD_ID 构建时间：16:03
src/app/jobs/[id]/CategorySelect.tsx 修改时间：16:14   ← 晚 11 分钟
```

→ 启动的是**旧生产构建**，新页面（删除按钮、类别列、定位列）根本没打包进去。
这是"改了代码忘记 rebuild"的典型坑，而启动器没有提示。

### 43.3 修法

| 项 | 做法 |
|---|---|
| 构建过期检测 | `buildIsStale()`：取 `src/**`、`package.json`、`next.config.mjs`、`tsconfig.json` 的最晚 mtime，与 `.next/BUILD_ID` 比较；源码更新 > 1s 即判定过期 |
| 行为 | 过期则**自动重新构建**并打印原因（"源码比构建新约 N 分钟"）；`--rebuild` 仍可强制 |
| 提示 | 构建跳过时打印"构建产物是最新的，跳过构建"，不再静默 |
| 文档 | getting-started 故障表补"页面没变化/看不到新按钮"条目 |

### 43.4 验证

```
node scripts/local-start.mjs --dry-run
▶ 构建（源码比构建新约 12 分钟（改了代码没重新 build）；约 1–2 分钟）
✅ dry-run 结束（未执行任何命令）
```

### 43.5 教训

"有构建产物就跳过构建"对**开发者自己**是省时间，对**用户验收**是灾难：验收的人不知道要 rebuild，
看到的永远是旧界面，然后报告"没有这个功能"。启动器必须能**自证产物新鲜度**。

## 46. 第四十六轮：Excel 另存 CSV 的 GBK 编码 bug（同步被拒）（2026-11-15）

### 46.1 现象

用户点「同步回库」后页面报：**「表头缺少「岗位ID」列，已拒绝同步」**，同步结果全 0。

### 46.2 根因

检查磁盘主表前 3 字节：`b8 da ce` = 「岗」的 **GBK** 编码，不是 UTF-8。
**中文版 Excel 另存为 CSV 时默认使用 ANSI（GBK）编码**；我们的同步只按 `readFile(..., "utf8")` 读 → 整表乱码 → 认不出表头 → 拒绝同步（这是保护逻辑，但误伤了正常流程）。

### 46.3 修法

| 层 | 做法 |
|---|---|
| 解码 | 新增 `decodeCsvBuffer()`：BOM（UTF-8/UTF-16LE）→ 严格 UTF-8 → 回退 **GB18030**（GBK 超集） |
| 同步 | 读主表改用解码器；若编码非 UTF-8，在报告里提示"检测到 gb18030（多为 Excel 另存所致），已自动解析；下次导出写回 UTF-8" |
| 导出 | 读已有主表（保留用户自建列）同样走解码器，GBK 文件里的自定义列也不会丢 |
| 测试 | 新增 `tests/csv-encoding.test.ts` 4 例（UTF-8 BOM / UTF-8 / UTF-16LE / GBK 回归） |

### 46.4 真实台账验证

```
npm run workspace:sync -- --dry-run
   更新 1 · 新增 0 · 跳过 0 · 冲突 0 · 未导出新增 0 · 受保护删行 0
   · 将更新：绿联科技 / CV小模型实习生（salary_min, salary_max）
   ⚠️ 检测到台账编码为 gb18030（多为 Excel 另存 CSV 所致），已自动按该编码解析；下次导出会写回 UTF-8。
```

> 那条 salary 更新是因为库里有脏值（1000/9999）而表格为空——同步会清空它，属预期。

### 46.5 教训

CSV 不是一个"格式"，而是一族地区性编码：同一份表在中文 Excel 里另存就可能变 GBK。
**只要程序读的是"用户会用 Excel 编辑的文件"，就不能假设 UTF-8**；要么自动识别编码，要么强制用户另存为 CSV UTF-8（我们两者都做了：自动识别 + 文档建议）。
