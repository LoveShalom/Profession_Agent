### 12.3 R1-03 引发的设计面（本次新增）

用户一句"允许用户修改"使工作区从"导出视图"升级为**第二编辑面**，必须补齐：

- **列级权限**：同步键只读 / 抽取字段可改（= 人工校准）/ 用户字段可改 / 计算字段只读 / 未知新列保留；

### 13.3 关键设计取舍

1. **三态而非"必填/空"两态**：`text_only`（"招满为止"）与 `absent`（完全没提）要分开——

2. **熟练度与必需性正交**：JD 里"熟悉 K8s 优先"= 加分 + 熟悉，"必须具备 Go"= 必须 + 未标注熟练度。
   合并成一个"难度等级"会丢失信息。
3. **熟练度必须可追溯**：每行技能带 `basis_phrase`（原文短语），没有就记 `unknown` 而不是猜。
   这是"幻觉抑制"原则（tech_stack §5）在技能维度上的延伸。
4. **差距分析依赖"我的水平"**：I1 阶段没有经历库（F-03 在 I2），因此需要 `我的技能.csv` 自评作为唯一输入；

**关键技术事实（必须记住）**：**CSV 无法保存单元格颜色**。先裁"用 CSV"，后提"要颜色"，二者在纯 CSV 下不可兼得。
最终裁决不是加 XLSX，而是**分列**——同一份 CSV 里用不同列承载"明确·必须 / 明确·加分 / 推测"，
既保留零依赖与单一数据源，又满足"一眼可区分 + 可按列筛选排序"。

**为什么"分列"优于此前的两种方案**：

| 方案 | 依赖 | 文件数 | 可编辑 | 可筛选 |
|---|---|---|---|---|
| CSV + 单元格颜色 | 不可能（纯文本） | — | — | — |
| CSV + XLSX 着色视图 | +1（exceljs） | +1 重复表 | 需分别维护 | 有限 |
| **CSV 分列（采纳）** | **0** | **不变** | ✅ | ✅ 列级筛选/排序 |

**容量缺口**：I1 44h 使总工时达 **214h**，超 200h 预算 14h。已在 `roadmap.md` §5 列出三种方案，

不是"入库闭环"的必要条件。待用户拍板。

## 17. 第十七轮：多模型路由（文本 / 视觉分开配）（2026-10-25）

### 17.1 需求

> "可不可以改成支持多个API的模式，需要图像模型的时候就调用图像模型。"

> ⚠️ 2026-10-25 复核：DeepSeek `deepseek-flash`（V4.1-Flash）**已支持 Vision**（官方定价页 Vision ✓）。
> 因此"DeepSeek 没有视觉模型"的前提已不成立，`supportsVision` 已更新为识别 `deepseek-flash`；
> 价格与选型见 §18。

**动机（也是设计依据）**：文本模型与视觉模型的性价比结构不同。
日常抽取要便宜快、读图要视觉能力，两者单价差一个量级。
一套配置逼用户在"便宜"和"能读图"之间二选一——这是配置缺陷，不是功能缺陷。

### 17.2 方案（采用：两组 env 配置 + 内部通用 router）

| 组 | 键 | 用途 | 留空行为 |
|---|---|---|---|
| 文本 | `LLM_PROVIDER` / `LLM_API_KEY` / `LLM_MODEL` / `LLM_BASE_URL` / `LLM_MODEL_EXTRACT` / `LLM_MODEL_GENERATE` | 抽取、生成、校验 | `LLM_PROVIDER` 默认 `deepseek` |
| 视觉 | `LLM_VISION_PROVIDER` / `LLM_VISION_MODEL` / `LLM_VISION_API_KEY` / `LLM_VISION_BASE_URL` | 截图识别（`/api/ocr`） | **未配置 = 截图识别不可用**，文本功能不受影响 |

**关键实现取舍**

| 取舍 | 理由 |
|---|---|
| 视觉 env **派生**自文本 env（override provider/baseUrl/model/key） | 直接复用 F-01 全套适配层：出站白名单、私网保护、重试、用量记账、降级链**零重写** |
| 派生时清空 `LLM_MODEL_EXTRACT/GENERATE` | 否则任务级模型覆盖会把**文本模型名**套到图片请求上（很隐蔽的 bug） |
| `LLM_VISION_API_KEY` 留空继承 `LLM_API_KEY` | 同一家服务商（如都用 Qwen）只需填模型名，少一处密钥管理 |
| 视觉 profile 创建失败**不抛 500** | 折成 `info.vision.reason`，API 返回可操作提示（未知 provider / custom 缺 baseUrl / 私网未开） |
| **不偷偷降级**到文本模型 | 文本模型读不了图，静默降级会得到"识别为空"这种假故障；必须明确报"当前模型不支持读图"并给候选模型 |
| 对外 2 个命名 profile，对内 `createModelRouter(env)` | 等 F-07（BYOK 设置页）落地，`user_llm_credentials` 的任意多条凭证可接进同一个 router，调用方不改代码 |

### 17.3 不做什么（防止范围膨胀）

- **不做 N 个任意 profile 的 UI 与持久化**：属 **F-07 BYOK 设置页（I2，4h）**；本轮只做两组 env
- **不做按任务自动选模型**（如"生成用强模型"）：已有的 `LLM_MODEL_EXTRACT/GENERATE` 已覆盖
- **不做视觉模型失败后自动换另一个视觉模型**：需要凭证池，属 F-07 之后
- **不引入本地 OCR**：Q-09 已裁决 A，保持不变

## 19. 第十九轮：方案 A 落地与“哪个模型”实测定论（2026-10-25）

### 19.1 用户裁决

> “做方案A” —— 单个 DeepSeek Key，文本与视觉都走 DeepSeek。

### 19.2 ⚠️ 实测发现：同 Key 下 deepseek-flash 不适合做文本抽取

同一段 JD、同一套规则、sampleK=1 对比：

| 模型 | 抽取路径 | 待确认字段 | 耗时 | 结论 |
|---|---|---|---|---|
| `deepseek-flash` | **L2（结构化输出两次校验失败 → 规则兜底）** | **12 个** | 1.4s | 快，但**白花模型调用**且质量差 |
| `deepseek-chat` | **L0（tool calling 一次成功）** | **6 个** | 3.0s | 慢一倍，但**AI 真正生效** |

**采用配置（方案 A 实测优化版）**：

```ini
LLM_PROVIDER=deepseek
LLM_MODEL=deepseek-chat          # 文本：L0 tool calling
LLM_VISION_PROVIDER=deepseek
LLM_VISION_MODEL=deepseek-flash  # 视觉：支持读图
LLM_VISION_API_KEY=              # 留空 = 继承同一个 Key
```

一个 Key、两个模型名，各取所长。**不要**把文本也切到 flash——待确认会从 6 个涨到 12 个。

### 19.3 端到端实测（真实 API，非 mock）

用 Pillow 渲染一张 900×1180 的 JD 截图（中文微软雅黑），跑完整链路：

```

          → deepseek-chat 抽取：level=L0 tool_calling，6 待确认 / 0 阻塞
公司=某科技有限公司 | 岗位=后端开发工程师 | 城市=上海/杭州
薪资=15000-25000 · 14薪 | 学历=本科 | 届别=2027
截止=provided 2026-11-20T23:59:59+08:00
技能=Java[must]/MySQL[must]/Redis[must]/Kubernetes[nice]/PyTorch[推测]/TensorFlow[推测]
关键项 6/6 通过
```

> 附带验证了原始需求：JD 只写“深度学习” → 推测 PyTorch/TensorFlow，在截图链路上同样成立。

### 19.4 新增可重复验收工具

`npm run verify:ocr -- --image <截图路径> [--report <输出>]`

### 19.5 成本实测结论

一次“截图 → 入库”全程（OCR + L0 抽取）约 **¥0.02**；100 条 JD/月 ≈ **¥2**。

### 20.2 设计取舍

- **不用 `.env` 存工作区目录**：`.env` 里有密钥，运行时业务改写它风险高（编码/并发/误删）；独立配置文件更安全

- **API 与 CLI 共用业务函数**：`exportWorkspace` / `syncWorkspace` 是唯一实现，两条入口行为保证一致
- **附件保存失败不阻塞识别**：截图存档只是证据，识别结果才是主产物
